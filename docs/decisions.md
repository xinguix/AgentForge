# AgentForge 技术决策记录（ADR）

> 本文档记录了 AgentForge 项目中的关键技术选型及其背后的考量。  
> 时间：2026年8月  
> 作者：孙枫凯

---

## 1. 为什么选 LangGraph 而不是 LangChain Chain？

### 决策背景
项目需要一个支持**多智能体协作**、**状态管理**和**条件分支**的工作流引擎。传统的 LangChain Chain 是线性的（A → B → C），无法满足“Reviewer 不通过则回到 Research 重试”的闭环需求。

### 决策方案
**选择 LangGraph 作为工作流编排框架。**

### 理由
| 维度 | LangChain Chain | LangGraph |
| :--- | :--- | :--- |
| **执行模式** | 有向无环图（DAG），单向流动 | 有向图（支持环），条件边可实现循环 |
| **状态管理** | 通过 `RunnablePassthrough` 手动传递 | 内置 `StateGraph`，全局状态自动管理 |
| **断点恢复** | 不支持 | 支持 Checkpointer（本项目用 AsyncPostgresSaver 持久化到 PostgreSQL，可跨会话恢复） |
| **可观测性** | 依赖外部回调 | 内置 `astream_events` 可细粒度追踪 |
| **多智能体** | 需要手动编排 | 原生支持 `add_node` 和条件路由 |

### 结论
LangGraph 的**图结构**和**状态管理**完美契合了 Multi-Agent 系统的需求，尤其是 Reviewer → Research 的自我修正闭环，在 LangGraph 中只需一行 `add_conditional_edges`，而 Chain 需要复杂的包装逻辑。

### 权衡
- **学习曲线**：LangGraph 比 Chain 复杂，需要理解“图”、“节点”、“条件边”等概念。
- **生态成熟度**：LangGraph 相对较新，但 LangChain 官方正在全力推进，前景明确。

## 2. 为什么选 PostgreSQL + pgvector，而不是专门的向量数据库？

### 决策背景
项目需要存储文档的向量嵌入（Embedding），并支持高效的相似度检索。可选方案包括：专门的向量数据库（Milvus / Qdrant / Pinecone）和关系型数据库的向量扩展（PostgreSQL + pgvector）。

### 决策方案
**选择 PostgreSQL + pgvector 扩展。**

### 理由
| 维度 | 专用向量数据库（Milvus） | PostgreSQL + pgvector |
| :--- | :--- | :--- |
| **运维成本** | 需要额外部署、监控、备份 | 复用现有 PostgreSQL，一套运维标准 |
| **一致性** | 向量数据 + 业务数据分离，可能不一致 | 同一事务可同时写业务数据和向量数据 |
| **查询灵活性** | 只支持向量检索 | 支持混合查询：SQL 中先按 `user_id` 过滤，再 `ORDER BY embedding <-> :query_vec LIMIT 5`（余弦距离排序） |
| **生态** | 需要额外学习 API | SQL 标准，开发者熟悉 |
| **性能** | 百万级向量检索更快 | pgvector 在 10 万级向量内表现足够，当前实际规模约百个文档块，远未触及瓶颈 |

### 结论
对于中小规模的 RAG 应用（文档数 < 1 万），PostgreSQL + pgvector 是**运维成本最低、开发体验最好**的方案。它让我们可以**在同一事务中**同时更新任务的 `status` 和文档的 `embedding`，保证数据一致性。

### 权衡
- **扩展性**：当向量数超过 100 万时，pgvector 的性能可能下降。届时可迁移到 Milvus，但当前阶段无需过早优化。
- **功能**：pgvector 不支持 GPU 加速检索，但 CPU 足够处理当前规模。

## 3. 为什么选 Redis？

### 决策背景
任务创建时需要保存一份「初始状态快照」供运行期状态查询使用；这类数据是易失的（任务结束后即可丢弃），且要求自动过期、不占用数据库。

### 决策方案
**选择 Redis 作为缓存层。**

### 理由
| 维度 | Redis | 直接查 PostgreSQL |
| :--- | :--- | :--- |
| **读写速度** | 内存级（微秒） | 磁盘级（毫秒） |
| **数据结构** | 支持 String / Hash / List / Set | 仅 SQL 表 |
| **TTL（过期时间）** | 原生支持 `SETEX` | 需要手动实现清理逻辑 |
| **热数据隔离** | 自动淘汰冷数据 | 需要额外索引策略 |

### 结论
实现中，任务创建时将初始状态快照以 JSON 写入 `task:{task_id}:state`（`SETEX` 写入即带过期时间），任务结束后删除，天然实现「用完即弃」。运行期节点级状态则由 LangGraph Checkpointer（AsyncPostgresSaver）持久化到 PostgreSQL，保证不丢失。

### 权衡
- **单点风险**：当前单机部署，无高可用；但状态快照易失、可重建，影响可控。
- **持久化**：Redis 数据可能丢失（AOF 模式下可缓解），但快照丢失后任务可重新发起，不是关键数据。

## 4. 为什么选 BGE 本地模型而不是 OpenAI Embedding API？

### 决策背景
项目需要将文档片段转换为向量。可选方案包括：OpenAI `text-embedding-ada-002`、Cohere 等商业 API，以及 BGE、M3E 等开源本地模型。

### 决策方案
**选择 BAAI/bge-small-zh-v1.5 本地模型。**

### 理由
| 维度 | 商业 API（OpenAI） | 本地模型（BGE） |
| :--- | :--- | :--- |
| **数据隐私** | 文档需上传至 OpenAI 服务器 | 所有数据留在本地，无外传风险 |
| **成本** | $0.02 / 1M tokens | 免费（仅需硬件电费） |
| **延迟** | 网络延迟 ~200-500ms | 本地 CPU 延迟 ~50-100ms |
| **中文优化** | 通用模型 | BGE-small-zh 专门针对中文微调 |
| **可控性** | 依赖外部 API 稳定性 | 完全自控，无速率限制 |

### 结论
考虑到企业知识库对**数据隐私**的高要求（文档可能包含敏感商业信息），本地模型是必选项。BGE-small-zh-v1.5 输出 512 维向量，模型文件本身约 100MB，CPU 可流畅运行，在**精度**和**资源消耗**之间取得了最佳平衡。

### 权衡
- **精度上限**：本地模型在中文检索评测（C-MTEB）上与 OpenAI 通用 embedding 模型基本相当，差距对 RAG 场景影响可接受；若需要更强语义理解，可升级到 bge-large-zh-v1.5。
- **硬件要求**：需要至少 2GB 内存加载模型。

## 5. 技术栈全景总结

| 技术 | 用途 | 选择理由 |
| :--- | :--- | :--- |
| **FastAPI** | Web 框架 | 异步原生、自动文档、依赖注入 |
| **LangGraph** | 工作流编排 | 支持图结构、条件分支、Checkpointer |
| **PostgreSQL + pgvector** | 主数据存储 + 向量检索 | 一套数据库、混合查询、事务一致性 |
| **Redis** | 任务状态快照缓存 | 高性能、`SETEX` 原生 TTL 自动过期 |
| **BGE-small-zh** | 本地 Embedding | 数据隐私、免费、中文优化 |
| **DeepSeek API** | LLM 生成 | 性价比高、兼容 OpenAI 接口 |
| **Docker Compose** | 部署 | 一键启动、环境一致性 |

## 7. 写在最后

技术选型没有“标准答案”，只有“最适答案”。AgentForge 的每一个技术选择，都遵循了以下原则：
1. **简单优先**：能用一个组件解决的，不用两个。
2. **数据隐私**：企业数据不外传。
3. **开发效率**：快速迭代，不追求过度设计。
4. **可观测性**：每一步都可追踪。

这些原则指导了所有技术决策，也将在未来的演进中持续发挥作用。
